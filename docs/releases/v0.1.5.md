<a id="release-verification-behavior"></a>

## Behavior of release verification

Workload release uses user systemd lifecycle state and cgroup v2 evidence instead
of a total GPU memory threshold. Stopped workloads must have `ActiveState=inactive` and `SubState=dead` with an
empty configured cgroup subtree (or a removed subtree). Missing, malformed or
unreadable evidence and mismatched manager metadata fail closed. Unrelated GPU
allocations do not affect this release check. Cgroup evidence proves process exit. It does not prove completion of asynchronous driver cleanup.

Live-media unload has no trustworthy completion verifier. An HTTP
success response alone is insufficient, so this path fails closed. Use
`-media-stop-mode stop-service`, or explicitly stop media before recovery. The UI is unavailable while its service does not run.

## Configuration migration

Remove `-release-max-used-mib`, including explicit `=0`. The controller rejects the flag.
Configure `-text-cgroup` and `-media-cgroup` consistently for every controller
sharing the state store. Use the canonical, distinct, non-overlapping paths of
the actual user systemd units within the host `/sys/fs/cgroup` hierarchy. The
active root slice of the user manager must strictly contain both paths. The controller does not support nested mounts or container mappings.

Optional `-text-required-mib`, `-media-required-mib` and
`-capacity-headroom-mib` checks separately assess pre-start capacity. They do not
reserve memory or replace release verification. Repair a capacity failure before
explicit recovery. Boot reconciliation does not resume interrupted work or take
control away from user ownership.

Execution proxies no longer implicitly forward GET, HEAD or OPTIONS. Before
upgrading, inventory every route and configure each verified read-only method and path
with `-read-only-route`. Keep execution and editing mutations explicitly classified.

Unknown routes fail closed. HTTP acceptance, response completion and stream EOF
are not terminal execution evidence. Check the exact runtime version's routes and
completion semantics against the [adapter contract](https://github.com/mickey-kras/gpu-workload-supervisor/blob/v0.1.5/docs/PROXY-CONTRACT.md)
before enabling execution. Generic repository tests do not qualify that deployment.

## Rollback and deployment limits

Do not downgrade in place against migrated state or mix controller and proxy versions
sharing a database. Keep a consistent pre-upgrade SQLite backup and matching
configuration and binaries. Before you restore state, stop proxies, automation and workloads.
Use `restore-state` to rotate the restored fence before reconciliation and before you restart proxies. See [the restore procedure](https://github.com/mickey-kras/gpu-workload-supervisor/blob/v0.1.5/docs/RESTORING.md). A restore
cannot stop work already executing outside the proxy, and ownership recovery
never restarts stopped user work automatically.

Artifacts target Linux amd64 and arm64 and include `gpu-mode` and
`gpu-workload-proxy`. Publication alone does not certify a host deployment,
runtime-specific execution and completion, or host acceptance tests. For qualification, record the verified source commit, successful release jobs and actual artifact digests separately.
These notes do not assert completion of those steps.
