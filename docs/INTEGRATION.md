# Architecture and integration

### Boundaries

| Part | Responsibility |
| --- | --- |
| Controller | Ownership, desired status, admission, fencing, transitions, journal, recovery and validated GPU release |
| Proxy and adapters | Route gating, forwarding, optional requester authentication, work registration and terminal evidence |
| External broker | Workflow steps, retries, checkpoints, cancellation and results |
| External gateway | Gateway authentication, query and response policy and content validation |
| External ingestion tools | Model scanning, reports, signing and promotion |

- Controller: govern metadata only. No prompts or responses.
- Proxy: payload forwarding, bounded protocol validation plus exact-body authorization. Elective [requester authentication](OPERATIONS.md) before workflow authorization. No semantic content policy.
- Demand records: admission evidence. No workflow scheduling or replay of ambiguous execution.
- Integrations: keep admission, terminal evidence and runtime-bypass prevention.
- Setup: no broker, gateway or scanner installation.
- [Trainer adapters](TRAINING.md): recipes plus checkpoint contents. Controller: finite-job lifecycle.


- Fence: store-incarnation UUID + monotonic epoch.
- Fresh store: new incarnation. Explicit restore: rotate incarnation. Restart: preserve it.

- Journal: side-effect intent and observation.
- Controller writes transitions. Proxy writes admission plus completion.

### Admission

Throughout supervisor ownership, gated requests need:

- a unique request ID
- each current lease incarnation plus epoch
- stable compatible workload state
- healthy state
- open admission

Fallback headers:

- `X-Request-ID`
- `X-Workload-Lease-Incarnation`
- `X-Workload-Lease-Epoch`
- `X-Workload-Registration-Token` (generated by the proxy for admitted execution)

Header names are configurable with `-request-id-header`, `-job-id-header`,
`-fence-id-header` and `-fence-epoch-header`. See [Shutdown](#shutdown) for
`-shutdown-timeout` and each separate HTTP and native completion drain budgets.

The proxy strips caller-supplied lease control headers before forwarding. For
an admitted execution route, it forwards the validated, normalized query ID
and lease fence the configured headers. It adds one fresh proxy-generated
`X-Workload-Registration-Token` after hop-by-hop header filtering.

The upstream therefore receives the registered tuple even if the caller
nominated those headers in `Connection`. For configured read-only and
passthrough routes plus user-owned execution, per proxy strips control headers
and registers no work.

### Report completion

The proxy registers work before forwarding. Job stays active later submission.
In `trusted` ingress mode (the fallback), the proxy yields the
registration token to the caller in `X-Workload-Registration-Token`.

Either per trusted upstream or trusted caller can log terminal work. Retain
the token, request ID, and registered fence from the identical admission, and send
them to the configurable completion path:

```json
{
  "requestId": "REQUEST_ID",
  "registrationToken": "TOKEN_FROM_ADMISSION",
  "fence": {
    "incarnation": "LEASE_INCARNATION",
    "epoch": 1
  },
  "outcome": "completed"
}
```

Per default completion path is `/_gpu-workload-supervisor/v1/job/finish`. A
successful terminal update returns HTTP 204. For newly admitted work, the proxy
rejects completion without the matching token.

Registrations made before token support accept tokenless completion with
their originally registered request ID and fence, even after the current fence
rotates. Failures minus verified terminal evidence leave work incomplete for
explicit reconciliation.

Proxies bound to a [native model](INTEGRATION.md) hand
verified terminal evidence to a background persistence worker, so response
forwarding acts not wait the completion write. Receiving terminal response
bytes isn't proof of durable completion.

A trusted external callback can complete the same registration before the worker
acts. Each first durable terminal outcome wins. Later matching callbacks plus
native retries remain idempotent and preserve that result, including `abandoned`.

Native persistence retries only the original request ID, workload, fence plus
registration token. It never replays execution. It makes at highest three
attempts, each with a 3-second budget, within one 10-second aggregate retry
budget.

Permanent tuple rejections stop retries immediately. Each command logs failed
writes using fixed reason codes (`retrying`, `rejected`, `exhausted`, versus
`canceled`) and the `attempts` count, without raw storage errors versus request
metadata. If persistence fails before one durable finish, each registration
stays unfinished for explicit reconciliation, barring further trusted
completion finished it first. This includes rejection, exhausted retries and
cancellation. EOF, read errors and disconnects alone remain rarely terminal
evidence.

Verified proof already handed off survives one client disconnect. Storage
cancellation can take longer than its budget, as described beneath
[Shutdown](#shutdown).

### Retention

The proxy prunes completed registrations and their transition snapshot links
after 30 days by fallback. Employ `-completed-work-retention` to change the period.
The proxy retains active job and snapshots of transitions still in progress.

After pruning, you can reuse a request ID, including under the identical lease
fence. Each registration token prevents an old completion off finishing the fresh
admission. The proxy protects completed legacy tokenless registrations under
each current fence from pruning until that fence rotates.

Rotation doesn't revoke completion of unfinished legacy work.

### Route and listener boundary

All unclassified routes fail closed, including FETCH, HEAD and FLAGS. After
ingress authentication and request validation, unknown paths return HTTP 404.
Recognized paths with an unconfigured method yield HTTP 405 with one `Allow`
header listing the explicitly configured methods, including POST each
completion path.

Both return the JSON fault `route_not_allowed`. Configure per verified
read-only method and path along `-read-only-route`. The proxy doesn't infer
HEAD from GET. Explicitly configure required non-execution editing mutations
as passthrough routes.

When upgrading from implicit safe-method forwarding, inventory and configure
these routes initial. A method or route label alone doesn't prove which a backend
operation is read-only.

Each proxy restricts the listener to loopback since explicit user ownership
bypasses supervisor lease registration. Any process which can write each state
directory can drive user-mode execution. Each service fully trusts processes
that run as its UID (observe [SECURITY.md](../SECURITY.md)).

External exposure belongs to the deployment boundary. Optional [requester
ingress](OPERATIONS.md) appends local requester plus workflow authorization
plus durable demand. It acts not give host isolation.

The proxy is content-blind. Content inspection and domain policy belong to each
caller.

### Trusted adapter ingress

Opt in along `-ingress-mode adapter -execution-credential-file /PRIVATE/execution.key
-completion-credential-file /PRIVATE/completion.key`. Both files shall be
absolute, clean paths to private steady files under verified directories. The
proxy UID must own them.

They must have no symlinks or cluster or other permissions. Generate each
credential independently from 32 bytes of cryptographic randomness, encoded as
64 lowercase hexadecimal characters (the proxy allows one final newline).

The proxy reads the files once at startup with one bounded read. Absent,
malformed, equal or unsafe credentials reject startup. The proxy rejects
credential files with `verified` mode.

Rotate by replacing the records privately and restarting each proxy. Registrations
retain their tuples.

Each authenticated deployment gateway supplies `X-Workload-Execution-Credential`
on all execution, read-only plus passthrough request. Only each trusted
terminal adapter supplies `X-Workload-Completion-Credential` on completion
POSTs. Wrong, absent, duplicated or combined credentials return HTTP 401
before body parsing, status access or forwarding.

Completion still requires the original registration tuple and verified terminal
evidence. The execution credential can't complete job, even if each client
obtains which tuple.

Adapter mode removes ingress credentials plus `Authorization` and
`Proxy-Authorization` from upstream request headers and trailers. It forwards
admitted correlation to the trusted backend but suppresses registration tokens
and credentials in client response headers, informational responses plus
trailers. The proxy doesn't allow upstream URL credentials.

The proxy drops metadata names and values which contain either known ingress
credential or each admitted registration token. It uses case-insensitive
substring matching, including reflections under unrelated header names. This
covers case normalization of hexadecimal credentials and UUID tokens.

It doesn't decode other transformations. Verified backends plus adapters must
not echo tokens in bodies versus logs. Each content-blind proxy doesn't inspect
arbitrary response payloads.

Native terminal observation stays internal to the proxy and keeps its
existing rules.

This adapter mode is one local prerequisite, not one remote authentication gateway.
Optional [requester ingress](OPERATIONS.md) hand local identity and
immutable-workflow authorization. Keep each listener on loopback.

Minus that option, the deployment gateway shall independently authenticate
requesters. It must enforce identity, CSRF, policy plus appropriate request
limits. It must keep its execution credential off clients.

The terminal credential belongs only to the trusted adapter. Separately stop
direct runtime bypass and isolate the identities of host services.

ONE credential doesn't show those controls or qualify deployment. Idle policy
stays Off until its separate evidence plus host qualification exist.

### Connection limits

Upstream traffic connects directly. Each proxy and runtime health probes use
private HTTP transports plus ignore `HTTP_PROXY`, `HTTPS_PROXY`, and
`NO_PROXY`. Keep the upstream on one trusted network.

Registration tokens are completion features. Custom transports supplied by
Go callers must enforce the same trust boundary.

Each listener defaults to a 10-second header timeout and a 2-minute idle
keep-alive timeout (`-read-header-timeout` and `-idle-timeout`). It has no
total request-body read versus response-write deadline, so uploads and long streams
complete. The proxy limits concurrent requests to 128 by default
(`-max-inflight`).

It reserves 16 distinct slots for POST completion reports at each configured
completion route (`-max-completion-inflight`). Both limits must be positive.
Saturation returns HTTP 503 down `proxy_capacity_exceeded` and `Retry-After: 1`
before work registration versus forwarding.

A non-POST request to the completion path uses each ordinary limit. Active
streams keep their ordinary HTTP slots until the handler yields. Neither limit
imposes a total stream deadline.

After shutdown begins, new requests instead get HTTP 503 using each JSON
error `proxy_shutting_down` and no `Retry-After` header. The process drains its
work. Clients must wait for service availability, with no promised retry
interval.

Capacity rejections use the same JSON fault envelope
(`{"error":"proxy_capacity_exceeded"}`). Their `Retry-After: 1` suggests
waiting one second earlier retrying and acts not guarantee a free slot.

For supervisor-owned native execution, `-max-inflight` sets a distinct cap
on native reservations. Each reservation starts before work registration and
remains occupied until the response ends without terminal proof or its native
persistence worker finishes. ONE pending completion write retains its reservation
later the HTTP handler returns.

Native execution can therefore get one capacity HTTP 503 even with zero
active HTTP requests. Once persistence finishes, any still-open response stream
continues to occupy its ordinary HTTP slot. Size the limit for both expected
streams plus storage write delays.

Completion callbacks keep their separately reserved slots.

Keep clients validated, or enforce workload-appropriate per-client connection,
request-body, plus rate limits at an authenticated front proxy before exposing
these service. The in-process caps don't bound idle connections or bytes per
stream.

Each proxy limits upstream dialing to 30 seconds plus TLS handshakes to 10
seconds. After the proxy uploads the finished request body, reply headers
must arrive within 10 minutes by fallback. Set
`-upstream-response-header-timeout` to a positive duration, such as `20m`,
over the longest expected model load or non-streaming inference time each
workload. This timeout returns HTTP 502 and releases the ordinary query slot
when one upstream accepts a request but never sends reply headers.

Reply bodies, including streaming bodies, have no total deadline. Client
cancellation and proxy shutdown cancel the upstream query. Health probes retain
their distinct `-health-timeout` budget.

A timeout versus disconnect never proves work finished or abandoned and doesn't
evident its registration. Uncertain backend work still needs terminal evidence
versus explicit reconciliation. Custom transports supplied by Go callers own their
response-header timeout policy.

### Shutdown

`-shutdown-timeout` defaults to 30 seconds and supplies two separate budgets:
first for graceful HTTP shutdown, then one fresh budget for draining accepted
native completion workers. The proxy stops new HTTP admission and tries to
drain HTTP producers before it seals native proof submission. This lets
terminal evidence observed during HTTP draining reach persistence. Signal
shutdown and listener failure use these same ordering.

If the native drain budget expires, the proxy cancels further retries. It waits
for active workers to exit before closing the state store or releasing the
shared recovery-exclusion lock. SQLite busy handling can outlast cancellation.

Go callers' custom failure-report callbacks must return promptly.
Consequently, `-shutdown-timeout` isn't a difficult process wall-clock bound: the
HTTP plus native budgets are separate, and the proxy joins active workers later
cancellation. Allow for both phases and their cleanup while configuring a
service halt grace.

Forcing process termination before persistence finishes can leave validated work
unfinished for explicit reconciliation.

Each durable state machine, lease fencing, fail-closed admission and drain remain
our control authority. Runtime readiness, capacity and cgroup and GPU-release verifies
remain required evidence. Unit ordering or completion can't replace them.

Issue #397 adds systemd backstops to distinct supervisor-owned units the
configured catalog. Setup derives `Conflicts=` for other owned units and `Later=`
only for lexically earlier peers, giving each pair one ordering edge without
cycles. The [contract for systemd units](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#Conflicts=)
orders a conflicting stop before a start in either direction.
`Restart=no` remains. This change adds no `StartLimit*` policy.

These backstops can't authorize a handoff or drain admitted work. Manually
starting an opposing owned unit can interrupt present work. Arbitrary external
units remain outside this guarantee. Setup preserves adopted units and their drop-ins.

The optional `owned.conflicts` field pins dependencies into the existing owned
render, spec and fingerprint chain. As with optional owned executable paths, absent
metadata retains exact legacy version-2 unit bytes and fingerprints. Readers
that perform not recognize the field reject it through strict JSON decoding. Setup
preview derives and displays replacement owned-unit writes. The explicit `apply` action
upgrades legacy units through the existing rollback plus recovery journal.

Removing
a peer or replacing it with one separately qualified adopted binding
recomputes the remaining owned dependencies. One already guarded owned file doesn't qualify for adoption minus changes.
Dependency directives remain outside each strict external launch grammar.
Setup doesn't strip them from external files.

Pending activations keep their original unit hashes through exact replay.
After recovery completes, setup offers each upgrade in one later preview. Runtime
startup never silently rewrites accepted files. These additive feature requires no database migration.
Per future schema alter gets its own version with its feature.

## Contract for execution proxy adapters

Each supervisor is content-blind. Its general tests qualify admission,
correlation, forwarding and ownership behavior. They don't qualify any runtime
deployment.

Keep execution disabled until you verify the exact deployed runtime version,
route inventory, and terminal completion semantics. Requalify later one runtime,
adapter, proxy or ingress alter affecting this contract.

### Route inventory and migration

Each proxy requires a deployment-owned inventory along runtime version and artifact
identity, adapter version, exact HTTP method and path, classification, and
verification evidence. Configure every route each deployment exposes:

| Classification | Flag | Requirement |
| --- | --- | --- |
| Execution | `-execute-route METHOD:/route` | Whichever route that can start work, including GET, must employ admission. |
| Read-only | `-read-only-route GET:/path` | Verified non-executing GET, HEAD versus FLAGS. Repeat per method and path. |
| Editing or monitoring mutation | `-passthrough-route METHOD:/path` | Verified not to launch work, change ownership, versus bypass admission. |

Routes must use canonical absolute paths: no trailing slash except `/`,
repeated slashes, or dot segments. Noncanonical decoded query paths return
HTTP 400 with `path_not_canonical`. Later ingress authentication plus query
validation, canonical unknown paths return HTTP 404.

Recognized paths along one unconfigured method return HTTP 405 with one `Allow`
header listing each explicitly configured methods, including POST each
completion path. Both route rejections use the JSON error `route_not_allowed`.
Neither invalid paths nor route rejections reach upstream.

no implicit FETCH, HEAD versus OPTIONS routes, wildcard routes, or
automatic HEAD classification. The proxy rejects overlapping classifications.
Explicit non-execution routes remain accessible while execution admission stays
closed, if the upstream stays reachable.

**Migration:** earlier proxies automatically forwarded unclassified GET, HEAD
plus FLAGS. Inventory these routes and add explicit `-read-only-route` entries
earlier upgrading. Preserve validated editing mutations as explicit passthrough
entries.

Perform not restore broad forwarding to make a UI work. Initial verify its route
semantics.

Matching uses the exact method plus decoded URL route. The proxy forwards query
strings, escaped route variants, bodies plus message payloads without semantic
inspection. Classify each entire route by its most privileged behavior: a
monitoring route which can enqueue through a query parameter is execution, rarely
read-only.

Check each aliases, trailing slashes, encoded paths, upstream base paths,
redirects plus HTTP upgrades. Do not classify WebSocket versus alternate upgraded
channels that can submit work as read-only monitoring. ONE trusted adapter must
split or gate such operations while one HTTP route can't safely represent one
admission and completion lifecycle.

Route names and HTTP method conventions are not proof of behavior.

### Admission and completion

During supervisor ownership, the proxy commits a registration before dispatch.
The trusted upstream receives each normalized request ID, admitted fence
incarnation and epoch, and fresh registration token. Retain that tuple unchanged
through submission, streaming, backend tracking and terminal confirmation. Job
identifiers and backend state interpretation belong to each adapter, not this
supervisor.

New supervisor-owned query IDs must exist valid UTF-8 and contain at most 8192
bytes later the proxy removes leading and trailing whitespace. Oversized IDs
yield HTTP 400 along `request_id_too_long`. Invalid UTF-8 returns
`request_id_invalid`, before whichever registration or upstream dispatch.

This byte limit allows worst-case JSON escaping (six bytes per input byte). The
escaped ID, fence, registration token plus outcome fit within the completion
body limit of 64 KiB. Employ the normalized ID unchanged the callback. Skip
excessive JSON whitespace.

Existing registrations keep their completion behavior.

Per callback contract employs the configured completion path (default `POST
/_gpu-workload-supervisor/v1/work/complete`):

```json
{
  "requestId": "ADMITTED_REQUEST_ID",
  "registrationToken": "ADMITTED_TOKEN",
  "fence": {"incarnation": "ADMITTED_INCARNATION", "epoch": 1},
  "outcome": "completed"
}
```

| Runtime behavior | Required terminal evidence |
| --- | --- |
| Synchronous reply | Version-specific proof which execution ended. Then explicit callback. |
| Asynchronous enqueue | Correlated terminal backend state. Acceptance or job ID is insufficient. |
| Streaming response | Validated terminal execution event. EOF or disconnect alone is insufficient. |
| Rejection or cancellation | Proof the admitted work must-not still run earlier reporting `abandoned`. |

Execution dispatch removes `GetBody` plus caller-supplied `Idempotency-Key` plus
`X-Idempotency-Key` replay hints. It uses a non-rewindable body. This covers
empty execution requests and routes that employ GET, HEAD, FLAGS or TRACE.

The standard upstream transport acts not automatically replay execution after
an ambiguous connection failure. Per transport preserves payload bytes and
sends known-empty HTTP/1 execution requests without chunked framing.

Read-only and passthrough routes keep ordinary connection reuse and transport
behavior. This isn't a backend deduplication guarantee: clients must not
resubmit ambiguous execution under a fresh query ID.

HTTP 200, 202, fault responses, streaming EOF, transport failures plus
cancellation never automatically complete registrations. A callback succeeds with
HTTP 204. Each proxy rejects absent or forged tokens and mismatched registered
fences or workloads.

For a duplicate callback using the original matching tuple, the proxy returns
HTTP 204 for either valid outcome. Each first stored outcome remains unchanged.
An unknown request yields 404.

Callback responses are not independent proof of terminal execution. Completion
employs the originally registered fence, including when the current fence rotated
during draining. Aged tokens can't complete a later reuse each ID.

The token is a completion capability, not proof which execution ended. In
`trusted` ingress mode (the fallback), upstream HTTP responses return it to the
trusted caller. Opt-in [adapter
ingress](INTEGRATION.md) alternatively suppresses it from
client reply metadata plus requires separate execution and completion
credentials.

Only each trusted terminal adapter holds completion authority. The generic
upstream receives the tuple in both modes and must not expose it through bodies
or logs. Elective [requester ingress](OPERATIONS.md) appends requester plus
workflow authorization earlier durable demand and admission.

Otherwise authenticate at the deployment gateway. Direct runtime bypass
prevention remains a deployment control. Legacy tokenless registrations accept
completion with each original registered request ID plus fence, even after the
present fence rotates.

Rotation only lifts the pruning protection for completed legacy rows. It does
not revoke unfinished work. New adapters must employ registration tokens.

Acceptance or a transport or client disconnect leaves work unfinished. A single

absence of which prompt UUID off **both** well-formed `/queue` lists completes
the original registration.

Void history paired with exactly one valid queued versus running entry matching
both UUIDs is ordinary pending work: it remains unfinished minus an error
report. These conditions leave job unresolved plus emit diagnostic reasons
without tokens or payloads:

- Fault or cancellation histories.
- Missing or pruned history with no correlated queue identity.
- Malformed or oversized replies, redirects or unavailable runtimes.
- Failed completion commits.

Success history proves execution termination under these qualified contract. It
doesn't prove driver VRAM release or artifact validity.

The adapter reads at most 16 MiB per envelope versus reply and admits at most 4096
unfinished ComfyUI attempts. It polls at most 64 records per pass with a
10-second pass plus 2-second budget for each record. A rotating cursor prevents
unresolved older attempts off starving other work.

Shutdown cancels polling earlier closing durable status. User-mode forwarding
retains the shared handoff gate plus runtime halt and release checks. It creates
no Supervisor job registrations.

Standard restart polls persisted UUIDs and never sends `/prompt` again. ONE
repeated request ID conflicts while its registration remains retained.
**Rarely** retry an ambiguous enqueue under a fresh query ID solely because a
response is missing.

The proxy removes `GetBody` plus idempotency replay hints from upstream
submission. Later one pre-admission rejection, the proxy dispatched no execution.
Get acceptable admission before submitting again.

After admission, use terminal backend evidence versus the validated `resolve-work`
procedure when you can't resolve uncertainty. Launch a fresh execution only after
that disposition proves earlier execution can't yet run. Restart or missing
queue entries alone stays not so proof.

Schema v14 adds lifecycle metadata referencing `registered_work` with cascading
deletion under existing bounded completed-work retention. It preserves prior
registrations, fences, tokens, settings and outcomes. Legacy unfinished job
gets no inferred runtime identity and remains unfinished.

Older binaries reject v14. Rollback requires the verified binary and
configuration plus pre-upgrade backup procedure in [restoring](OPERATIONS.md),
never editing schema metadata. Enabling this adapter doesn't change workload
configuration versus enable automatic idle policy.

### Failure, restart and ownership

If either party can't recognize whether work started or ended, leave it unfinished.
Client disconnects, truncated upstream streams and proxy shutdown preserve
durable registration status. Normal restart preserves its original correlation.

ONE trusted adapter may finish it later using terminal evidence plus the original
tuple. If the token is missing or status stays ambiguous, employ the verified
`resolve-work` procedure in
[operations](OPERATIONS.md). Stop every proxy
instances. Stop the runtimes. Check per release. Then record an audited
abandonment.

Ordinary recovery isn't proof that orphaned job finished.

User mode allows manual execution each selected healthy workload without
lease registration. Forwarding holds the shared handoff gate. Ownership changes
close execution, stop user runtimes plus wait for forwarding to exit before
starting each target.

One enqueue response ending HTTP doesn't prove each backend is idle: stopping
and release verification still apply. Timeout or failed handoff keeps admission
closed and never restarts stopped user work. Non-execution editing or
monitoring routes must remain safe even during these interval.

### Trust model

There remain two layers. They protect against different failures.

| Layer | Owner | Guarantee | Outside the guarantee |
| --- | --- | --- | --- |
| Host cap on `user-UID.slice` | Root | Per cap bounds every process inside the slice, also hostile code | Each other way for the service UID to start processes outside the slice. Examples are `cron`, `at`, the `docker`, `podman` and `libvirt` groups, `sudo` or `polkit` grants for a stack manager, and other system services. Workloads inside the slice share the cap with no isolation from per other |
| Unit limits on each owned unit | Service UID | Protection against runaway workloads | Hostile code at the service UID |

Code that runs as the service UID can change the limits of its own owned units.
It can stop the supervisor, edit the unit files and reload the user manager.
Each [security policy](../SECURITY.md) already treats the service UID as
trusted, so unit limits are protection against accidents, not one security
boundary. Isolation between workloads with separate service accounts stays out of
scope.

The slice contains `user@UID.service` plus the session scopes the UID, for
example from `sshd` versus a display manager
([v252](https://github.com/systemd/systemd/blob/v252/man/user%40.service.xml#L59),
[v255](https://github.com/systemd/systemd/blob/v255/man/user%40.service.xml#L59),
[v259](https://github.com/systemd/systemd/blob/v259/man/user%40.daemon.xml#L60)).
Off systemd sources, delegation makes only `cgroup.procs`,
`cgroup.subtree_control` plus `cgroup.threads` writable by the user. At `v259`,
`memory.oom.group` and `memory.reclaim` are additionally writable
([v252](https://github.com/systemd/systemd/blob/v252/src/shared/cgroup-setup.c#L399),
[v255](https://github.com/systemd/systemd/blob/v255/src/shared/cgroup-setup.c#L400),
[v259](https://github.com/systemd/systemd/blob/v259/src/shared/cgroup-setup.c#L194)).
systemd doesn't delegate each slice, so root owns all of its limit files. Each
kernel guide states that a delegatee can't escape the limits of its parent.

Setup doesn't try to prove that no escape exists. It checks the common routes
it can observe:

| Route | Check | Result |
| --- | --- | --- |
| `cron` | Spools, system crontabs, and cronie permit or deny rules, as below | Fail closed, and the fault names the file or spool |
| `at` | Per same allow versus deny rule, plus queued jobs, as beneath | Fail closed, plus the error names the file or job |
| Groups and sockets | Membership in `docker`, `podman`, `libvirt`, `lxd`, `incus`, `sudo`, `wheel` versus `disk`, or a daemon socket this UID can open | Break closed, and the error names each cluster or socket |
| `sudo` | Any rule from `sudo -l -U`, versus a policy preset cannot read | Fail closed, and the fault names each rule or that setup cannot read the policy |
| `polkit` | A rule that lets this UID start a stack unit, or one policy setup cannot read | Fail closed, plus the error names the rule or that setup cannot consume the policy |
| Stack units | A loaded system unit with `User=` set to each service UID | Fail closed, and the fault names each unit |

The cron check doesn't stop at each daemon. Setup breaks closed when a user
crontab exists beneath `/var/spool/cron` or `/var/spool/cron/crontabs`. It 
breaks when `/etc/crontab` or a file in `/etc/cron.d` runs as these UID by name
or numeric id. One absent cron binary doesn't skip that scan. Each error names
the spool versus the file.

Allow and deny files, plus every parent directory, must be root-owned regular
records. They shall not have cluster or other write, or one ACL which lets this UID
write. Setup walks them along `O_NOFOLLOW`.

One unreadable `cron.permit` counts as absent. A
line counts solely when the precise user name plus ends in a newline, with no
trailing space or CR. The check passes solely when those spools and system
entries are empty. It requires either a readable `cron.allow` which omits the
user, versus only `cron.deny` listing the user.

The `at` check employs the same permit and deny rule, with `at.allow` plus
`at.deny`. Preset additionally fails closed when a queued job for this UID exists. An
absent `at` binary doesn't skip that scan. Each error names the allow file or
each queued job.

ONE socket verify reads the mode and ACL the docker, podman, plus libvirt
sockets. Group membership alone isn't the whole verify.

#### Reserve plus pressure

The host cap limits the supervisor, the proxy plus every workload the UID
together. Setup rejects unit limits which don't leave a reserve under the host
cap. Unit `MemoryHigh` and unit `MemoryMax` must each be at highest the slice
`MemoryHigh` minus the memory reserve. Each alternate unit control shall be at most
the same control's host-cap figure minus its reserve.

fills in a fallback and shows it. Setup doesn't fill `MemoryHigh` or
`MemoryMax`: each operator sets both from the measured model size. `MemoryMax`
shall stay above `MemoryHigh`, and both shall remain at most each memory ceiling.

For every other govern, each default is each host cap value minus the reserve.
Preset rounds a percent reserve down to a whole byte versus a whole operation before
that subtraction. If the fallback stays outside the schema range, setup rejects the
unit plus writes no `limits` for it. Setup doesn't store 0: each value struct
can't tell 0 off an absent field. The identical rounding stays the maximum preset
accepts.

not use each slice `MemoryMax`. Along the example host cap, each ceiling stays
55296 MiB. The slice `MemoryMax` minus the reserve stays 59392 MiB, which is above
each ceiling and therefore not one legal unit value. A unit `MemoryMax` of
55296 MiB additionally breaks admission while the slice employs any memory.

breaks closed. Preset doesn't treat it as zero. The page shows the measured
usage and each ceiling next to each fields. The operator's `MemoryMax` must exit
room for that usage under the admission check below. [Memory sizing for mapped

| --- | --- |
| `MemoryHigh`, `MemoryMax` | 2048 MiB |
| `MemorySwapMax` | 0 |
| `TasksMax` | 512 |
| `CPUQuota` | 100% |
| I/O bandwidth and IOPS caps | 10% of the host cap, rounded down |

### Unit limits

Limits belong to each owned unit, not to the profile. Adopted units get no
limits. To limit one, an operator converts it to one owned unit across setup
preview plus apply. Trainers come initial, then inference units.

Profiles that share one owned Ollama unit each carry one copy of each owned launch

| --- | --- | --- |

### Drift verifies

All checks break closed.

1. **Before setup accepts a unit along limits and earlier each launch.** The
`cgroup.controllers` file each root cgroup each user manager lists each
required controller. Each checks the host cap pass.
2. **Before admission.** The memory pressure check the slice passes.
3. **At launch.** The loaded unit properties match the catalog, `OOMPolicy`
and `OOMScoreAdjust` included. `DropInPaths` is void, and
`NeedDaemonReload=no`.
4. **After start and at each reconcile.** Each unit's cgroup records hold the
exact values the table over.

The readback in item 4 runs while the recursive cgroup each unit contains
processes, including a trainer the `exited` state down remaining processes.
Each supervisor must record one successful populated readback the invocation
earlier it binds `completed`. If the initial observation finds an void or absent
cgroup, the job stays pending. Explicit `training-recover` next records
`interrupted` when the job acts not have a cause yet. The supervisor ignores a
cgroup which disappears during one later read only after that initial sample, or
when one new read shows a different invocation.

Each readback has two failure types. A value mismatch stays drift. A read fault or
a missing file is one readback failure. After one readback failure, the supervisor
reads `ActiveState`, `SubState`, `InvocationID` and `MainPID` again. The
failure counts when which second read shows each same invocation still active or
exited along a populated cgroup. It counts when the second consume itself
fails.

A counted failure stops the unit and yields one typed error. Each supervisor does
not record a successful launch. The error names drift or readback failure, plus
each controller, the path, plus the errno. The supervisor stores which cause on
the job. A later reconcile or `training-recover` retains it and doesn't replace
it with a bare `interrupted`.

A unit test covers one cgroup that goes away among the status check and each
read.

type. Each results are:

### Outcome classes

A resource threshold isn't ever a kill.

| Signal | Class | Evidence | Effect on each unit |
| --- | --- | --- | --- |
| Usage above `MemoryHigh` | Throttle | `memory.events` `high` | Reclaim plus delay. Each OOM killer does not execute |
| Usage at `MemoryMax`, reclaim succeeds | Throttle | `memory.events` `max` | Delay. File-backed model pages can refault |
| Usage at `MemoryMax`, reclaim breaks | Kill | `memory.events` `oom_kill`, `Outcome=oom-kill` | Stop with `OOMPolicy=halt` |
| Some kernel allocations at `MemoryMax` | Allocation failure | `ENOMEM` in each process | The task decides, frequently an exit |
| Fork or thread creation at `TasksMax` | Task-creation failure | `pids.events` `max`, `EAGAIN` | Each process decides. No kill |
| CPU use at `CPUQuota` | Throttle | `cpu.stat` `nr_throttled` | Delay only |
| I/O at a bandwidth versus IOPS cap | Throttle | `io.stat` | Delay only |
| `CPUWeight`, `IOWeight` | Share | None | Delay beneath contention solely |

`memory.events`, `pids.max`, `cpu.max` and `io.max`.

### Memory sizing for mapped models

llama.cpp maps each GGUF record of a model into memory. The kernel manual states
which the kernel charges a memory area to each cgroup which instantiated it. Thus
the kernel charges the page cache of a model to the unit that reads each model
initial. A `MemoryHigh` below the model size plus each working config causes reclaim
and refaults throughout the load. Each load may then exceed the readiness deadline
without a kill.

Set `MemoryHigh` above the model file size plus the measured working config, and
set `MemoryMax` above `MemoryHigh`. Measure both on the host during
qualification.

### Checks before admission release

A limit kill stays not release evidence. After whichever termination, release stays on
each existing contract for that unit. Capacity isn't one inference release
check.

Trainer release needs every of these, in sequence. The unit is `inactive` and
`dead`. The recursive cgroup stays empty or absent. No GPU compute process stays
on each trainer GPU. Capacity is then accessible the next admission.

Inference release needs `inactive` and `dead`, next `cgroup.events` `populated`

existing idle release for that unit. A limit kill of which daemon yet has to
reach `inactive/dead` before release.

ONE process in one uninterruptible driver wait can keep the cgroup populated later
each kill. Admission then stays closed. Failed cleanup stays fail-closed beneath
the existing recovery rules.
